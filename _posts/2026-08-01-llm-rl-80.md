### The problems

RL is typically used in three ways in modern LLMs.  
1) RLHF for alignment (eg. helpful, harmless, honest)  
2) RL with verifiable rewards (eg. math and code)  
3) RL with rubrics in subjective domains (eg. law)   

### The algorithms

A typical RL flow looks like the following: the agent has a policy (which is a probability distribution over actions), interacts with an environment by picking an action and then gets a reward. Based on the reward, the policy gets updated. For example, if it got a high reward, it will increase the probability it assigns to the action it just took. The agent keeps taking these actions (called turns) till the trajectory is over and it gets the final reward. The return is the sum of all the rewards in this trajectory.

For example, in a game of chess, the agent keeps making moves till the game is over (ending in either a win, loss or draw). Every move it makes is an action. Given a particular state of the board, all the valid moves that can be made constitute possible actions. There's no reward after each move but only at the last step, which is also equal to the return.

In the case of LLMs, each action is the next token being generated. So the policy is the probability distribution over the entire vocabulary.

In terms of algorithms, PPO and GRPO are the most common, former for RLHF and latter for RLVR. The newer ones (like DAPO, GSPO, etc) are minor modifications of the update formula.

We store multiple copies of the model in memory. The main two are the trainer and the generator/sampler.
The trainer is the model whose weights are updated via backpropagation and the generator is just used for rollouts. A rollout is the output from the LLM for a given training sample.

Depending on the implementation, there might be two more models.  
1) A "reference" model which is frozen before any RL and then used to measure the KL divergence to the policy. The KL divergence measures the difference between two probability distributions and acts as a check against the policy update being too big in one go.  
2) A "reward" model specifically for PPO (not GRPO) which assigns scores to actions. This is often a finetuned version of the LLM used as a proxy for human preferences. In GRPO, we replace this by the mean of several Monte Carlo estimates. A Monte Carlo estimate is just the LLM being run and we use the output (also known as trajectory).  

Every trajectory from the generator is used to update the model weights via backpropagation. All these are policy gradient algorithms, and there's a clean expression for the gradient using the [reparameterization trick](https://stillbreeze.github.io/REINFORCE-vs-Reparameterization-trick/). The trainer is the only model being updated.  

RL generally plays well with another algorithm called on-policy distillation but that's not covered here. It's a way to get more training signal from long rollouts.  

### The data

RL generally doesn't need any data. The algorithm needs an "environment" which responds to actions and changes its state. For example, if the model is solving a coding problem, the environment here is the sandbox which runs the code and returns the output. In some cases, before undergoing RL, the LLM is "primed" by supervised learning on pre-collected agent trajectories from datasets like OpenThoughts - sometimes known as "behaviour cloning". The rationale goes that the model learns quicker from RL if it's already been introduced to these trajectories earlier. RL is famously sample-inefficient so anything that helps us get more signal out of limited data (and sparse rewards) helps.

### The infrastructure

There're many modern RL frameworks since 2023. The most popular ones now are slime and SkyRL. Others include verl, vime, trl, torchrl, NeMO-RL and OpenRLHF. They're generally similar in architecture. First you pick the trainer (FSDP in SkyRL, Megatron in slime) and the generator (vLLM in SkyRL, SGLang in slime) and then you've an orchestrator between the two. The latter is responsible for scheduling rollouts, collecting the trajectories from the generator and sending them to the trainer, then copying the updated model weights from the trainer to the generator. The main infra challenge is the weight transfer. It's many GBs of data which need to be copied to a separate GPU. Intra-node transfers are usually fast because of NVLink/NVSwitch but inter-node is much slower via InfiniBand. If the transfer is too slow, the generator and trainer diverge, i.e. the trainer weights are too ahead of the generator ones, which makes the training [off policy](https://fengyao.notion.site/off-policy-rl). In general, there's an upper bound on the staleness allowed by the framework to achieve a balance between fully on-policy (very slow) and fully async (too divergent).  

The other main infra component is the environment, eg sandbox for coding agents. These are often long-running (eg. long horizon coding tasks over hours) and need to be brought up/shut down very quickly. They're generally Docker containers or similar virtualization technologies.

### Summary

RL has a very rich history (and a lot of mathematical theory). But modern RL on LLMs is a lot simpler, and the infrastructure bit is the tricky part. RL frameworks abstract out the math for the policy update.
